# pybaseball-nl-east

**Showcase: `pyduck-ona` × `pybaseball` on National League East rosters.**

A demonstration repository that takes the three [`pyduck-ona`](https://github.com/ezraair555/pyduck-ona) family packages — built for workforce HR analytics — and shows them working on **Major League Baseball roster data** instead. The org-chart structure, the compensation stream, the timeline events, and the natural-language query layer all compose with zero modifications to the underlying packages.

## Why this exists

`pyduck-ona` ships with HR-shaped examples — synthetic 30-employee orgs,
salary regressions, attrition models. This repo asks the question:

> **"If `pyduck-ona` is genuinely domain-agnostic, can it analyze a baseball
> roster the same way it analyzes a company?"**

**Answer: yes.** The same `DuckONA` connection that loads HRIS can load a
roster. The same `pyduck_ona.hierarchy_stats` that ranks managers by span
of control can rank position coaches. The same `pyduck_ona_profile.Subject`
that joins an employee to compensation/attendance/skills can join a player
to OPS/games-played/manager. The same `pyduck_ona_profile.ask()` that
parses "managers with the most direct reports" can parse "pitchers with
the lowest ERA" once you add the relevant query patterns.

The bigger argument this repo makes: **the org-analysis toolkit has been
waiting for non-HR data sources, and sports rosters are the perfect
test-bed because every player has a manager (coach), a salary (we use OPS
as a proxy since pybaseball doesn't ship salaries), and a tenure
(debut date).**

## Install

The three `pyduck-ona` packages are local checkouts in `../`:

```bash
git clone https://github.com/ezraair555/pyduck-ona         ../pyduck-ona
git clone https://github.com/ezraair555/pyduck-ona-viz     ../pyduck-ona-viz
git clone https://github.com/ezraair555/pyduck-ona-profile ../pyduck-ona-profile

pip install -r requirements.txt
pip install pybaseball==2.2.7
```

`requirements.txt` already references the local checkouts as
`-e /home/lucas/.openclaw/workspace/projects/pyduck-ona` etc. so the
`pip install` will pick them up.

> **First run note:** `pyduck-ona-profile` uses `BAAI/bge-small-en-v1.5`
> (~130 MB). It downloads on first call to `ask()` and is then cached.

## Run

The full pipeline is five commands, in order:

```bash
# 1. Pull NL East batting + pitching for every season, save as Parquet.
python -m nl_east.extract

# 2. Build a coaching hierarchy for every (team, season).
python -m nl_east.build_orgchart

# 3. The five showcases:
python examples/01_orgchart_overview.py
python examples/02_visualize_orgchart.py
python examples/03_player_profile.py             # Ronald Acuña Jr. by default
python examples/03_player_profile.py --player "Bryce Harper"
python examples/04_nl_queries.py
python examples/05_performance_models.py
```

After all six commands, the `outputs/` directory has 45 PNG figures, 18
interactive HTML dashboards, 7 CSV data dumps, and 5 Markdown reports.

## What each example shows

### `01_orgchart_overview.py` — pyduck-ona

Runs `hierarchy_valid`, `hierarchy_stats`, `hierarchy_long`,
`betweenness`, `pagerank`, `louvain_communities` against every
(team, season) org chart. Writes:

- `outputs/csv/hierarchy_stats_all.csv`
- `outputs/csv/betweenness_all.csv`
- `outputs/csv/pagerank_all.csv`
- `outputs/reports/01_orgchart_overview.md`

**Highlight:** every team's `L3-BULLPEN` coach has the highest span of
control and the highest betweenness centrality. They're the structural
broker for the pitching sub-tree.

### `02_visualize_orgchart.py` — pyduck-ona-viz

For ATL 2024 (focal), NYM 2023→2026 (year-over-year), and PHI
2023→2026 (year-over-year), produces:

- `span_of_control` (bar chart)
- `span_vs_depth` (quadrant bubble chart)
- `centrality_dashboard` (2×2 betweenness / PageRank / eigenvector / degree)
- `hierarchy_depth_heatmap` (employee × level matrix)
- `silo_map` (community-coloured network)
- `org_chart_tree` (interactive D3 HTML)
- `summary_dashboard` (single-page executive HTML)

Outputs land in `outputs/figures/` and `outputs/html/`.

### `03_player_profile.py` — pyduck-ona-profile Subject view

Picks a player (default: Ronald Acuña Jr.), loads the org chart as
`hris`, OPS as `compensation`, and games-played as `attendance`, then
renders:

- The `Subject.profile()` view at three roles (`hrbp`, `manager`, `self`)
- A `Timeline` with `comp_change` events for every year-over-year OPS move
- An `as_of` snapshot at a chosen date

**Note on the `Snapshot_date` column.** Every org-chart node carries a
`snapshot_date` (mid-season of the year the chart represents) so the
upstream `detect_manager_changes` and `detect_promotions` event
detectors can run without erroring out. Because each chart is a single
snapshot per `(team, season)`, the manager-change detector correctly
finds **zero** within-season changes — a player trading mid-season
would need two snapshots (a "before" and an "after" with the same
`employee_id` but different `supervisor_id`) for the detector to fire.

**Integration shim:** `Timeline._auto_detect` looks up loaded tables
via `getattr(ona, name)`, but `DuckONA` keeps tables in
`ona._table_names` rather than as public attributes. We expose the
relations explicitly after loading:

```python
ona.load_compensation(df)
ona.compensation = ona.con.sql("SELECT * FROM compensation")
```

This is documented inline; it's a real integration gap between the
two packages that may be worth filing upstream.

### `04_nl_queries.py` — pyduck-ona-profile ask()

Five baseball-specific `QueryPattern` objects added to the package's
`SEED_PATTERNS`:

- `top_hr_leaders` — "Who has the most home runs?"
- `low_era_pitchers` — "Pitchers with the lowest ERA"
- `most_strikeouts` — "Pitchers with the most strikeouts"
- `high_ops_hitters` — "Best OPS hitters"
- `cross_season_hr_trend` — "Year over year home run leaders"

Plus 2 HR-style sanity checks that match against the seeded pattern bank.

**Workaround:** the shipped `ask()` defaults any unresolved integer slot
to `12`, which is correct for `window_months` but wrong for `season`. We
wrap `ask()` with a small post-processor that detects the year from the
question and substitutes the correct season into the rendered SQL. The
fix is isolated to ~20 lines in `examples/04_nl_queries.py`.

**Sample result (similarity 0.838):**

> *Question:* "Who has the most home runs?"
> *Matched pattern:* `top_hr_leaders`
> *SQL:* `SELECT Name, Tm, HR, RBI, OPS FROM batting_2025 WHERE HR IS NOT NULL AND PA > 100 ORDER BY HR DESC LIMIT 10`
> *Top row:* Kyle Schwarber (PHI), 56 HR, .928 OPS

### `05_performance_models.py` — pyduck-ona stats

- **OLS** — `OPS ~ Age + log_PA + HR + RBI`, R² ≈ 0.61 across seasons
- **ANOVA** — `OPS ~ Tm` (NL East teams only): F = 4.14, p = 0.004 in 2023 (Atlanta's dominant year); p > 0.05 in 2024/2025/2026 (parity)
- **Logistic** — `is_all_star (OPS >= 0.800) ~ Age + HR + RBI + log_PA`

Outputs: `outputs/csv/ols_*.csv`, `anova_nl_east.csv`,
`logistic_*.csv`, and `outputs/reports/05_performance_models.md`.

## The coaching hierarchy

`pybaseball` doesn't expose coaching rosters, so we synthesise a
plausible 4-level hierarchy per team:

```
L1  Manager
    └─ L2  Bench Coach | Pitching Coach | Hitting Coach
          └─ L3  Bullpen Coach | Starters Coach | Infield Coach | Outfield Coach | 1B Coach | 3B Coach
                └─ L4  Players (assigned by role)
```

- Pitchers go to `STARTERS` (≥ 2 GS) or `BULLPEN`.
- Position players are split 50/50 between `INFIELD` and `OUTFIELD` via a
  deterministic MD5 hash of their `mlbID` (so the split is reproducible
  across runs and seasons).

The fixed coaching names per team are taken from recent MLB coaching
staffs; see `nl_east/coaching.py` for the full list. This is good enough
to demonstrate span-of-control, betweenness, and central player
detection; a real coaching tree could be hand-coded in the same place
without changing the rest of the pipeline.

## Known limitations

1. **No real coaching tree.** The hierarchy is synthetic. A future
   version could scrape or hand-code real coaching staffs.
2. **No salary data.** pybaseball doesn't include salary. We use OPS as a
   continuous "compensation" proxy for the `Subject.comp_history` view.
3. **Multi-stint trades are collapsed.** When a player appears for two
   teams in one season (`Tm = "Atlanta,Miami"`), we attribute them to
   their most-recent stint for the org chart. Trade-as-`manager_change`
   event detection is supported by the schema but not yet wired up —
   it would need two snapshots (before-trade and after-trade) for the
   same `employee_id`.
4. **2026 is partial.** Through 2026-06-27. Performance numbers will
   change as the season progresses.
5. **Two integration gaps with `pyduck-ona-profile`:** (a) the
   `Timeline._auto_detect` attribute lookup (worked around in example
   03), (b) the `ask()` integer-slot default of `12` (worked around in
   example 04). Both are isolated to small wrappers in their respective
   example files.

## NL East disambiguation

`pybaseball.batting_stats_range` and `pitching_stats_range` return
**every MLB player** in the date range, not just NL teams. The `Tm`
column is ambiguous for `"New York"` (Mets are NL East, Yankees are AL
East). We disambiguate by also requiring `Lev == "Maj-NL"` from
pybaseball's `Lev` column. In raw counts:

| Season | Batting rows (NL East) | Pitching rows (NL East) |
|--------|------------------------|--------------------------|
| 2023   | 104                    | 137                      |
| 2024   | 100                    | 141                      |
| 2025   | 100                    | 145                      |
| 2026   |  93                    | 115                      |

Before this filter the rows were inflated by ~40-60 per season (the
Yankees cohort). The disambiguation lives in
`nl_east/constants.py::is_nl_east_full_name_for_league`.
